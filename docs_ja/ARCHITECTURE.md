# 設計と要件

[English](../docs/ARCHITECTURE.md) | 日本語

## 対象範囲

用途の優先順位はサーバー・常駐処理 → ゲーム → デスクトップです。
初期版では開発中の更新を確実にし、本番更新・クラッシュ隔離・副作用の自動ロールバックは必須要件にしません。
所有と停止契約を中心に API を設計します。

実行経路は `RequestRouter` と版付きホストサービスに統一しました。
ネイティブロードと静的リンクの双方が同じハンドラー・資源・停止契約を使います。

## 所有と実行境界

| 所有者 | 保持するもの | リロード時 |
| --- | --- | --- |
| ホスト | Executor、接続、入力・送信キュー、画面・GPU 等の資源 | 維持し、ID とサービス操作でロジックへ公開 |
| ロジック世代 | DLL、関数表、世代固有データ | 実行が参照する世代を保持。既定では物理アンロードしない |
| 管理対象ルート | Future、入力コピー、資源・停止制御への所有参照、世代参照 | 完了または明示的なキャンセルまで保持 |
| 登録ワーカー | 安定した WorkerId、生成入力、最後のチェックポイント | Restart の再生成対象としてホストが管理 |

DLL 境界では C ABI の関数表・不透明ハンドル・呼び出し中のバイト列を使います。
各側で確保した Rust コンテナはその側で解放し、ホスト資源の `T` のレイアウトを DLL へ渡しません。
サービス ID・版とスキーマの一致は、データの意味や実装の正しさの証明ではありません。

タスクと資源レジストリは所有スレッドで作成・poll・破棄します。
Waker の別スレッドからの通知と、Future 自体の Send は別の契約です。
低水準 FFI の安全性は、信頼済みロジックが所有・保持・破棄契約を守ることを前提とします。

## 二つの切り替え方式

| 方式 | 旧実行 | 新規処理 | 適した用途 |
| --- | --- | --- | --- |
| Drain | 旧世代で完了まで継続 | activate 後は新世代 | 有限の要求・ジョブ |
| Restart | 停止通知 → 終了確認 → チェックポイント移行 | 登録ワーカーを新版で再生成し、受付状態を復元 | 常駐処理、再生成可能なゲーム処理 |

同じ接続を維持しながら次のメッセージでコードを更新するには、ホストが受信して要求ごとに受付先を選びます。
DLL 内の永続接続ループを Drain するだけでは、その接続の実行コードは更新されません。
同一ストリームを旧新世代が同時に読むことも自動では防げないため、ホストの所有規則を定めます。

Restart が移すのは明示したチェックポイントです。任意の Future のスタックや途中の実行位置は移しません。
通常リクエストは外部送信等の二重実行を避けるため再実行しません。
明示登録した子処理の停止・join はルートの終了待ちに含めます。管理外の子タスクや
コールバックは自動発見しないので、アプリケーションが終了を確認します。

## 状態と失敗

- 継続する共有状態はホストに置き、旧新世代が共存できるサービス契約を維持します。
- 世代内状態のうち移行が必要なものだけを、スキーマ ID・版付きのチェックポイントに保存します。
- Future のローカル状態はその実行世代に属します。途中更新と外部副作用は自動で巻き戻しません。

ビルド・候補検査の失敗では旧受付を維持します。
Restart は全ルートの終了と全移行・factory の成功を待ってから、新しいワーカー一覧を適用します。
停止後の失敗や Restart Future の Drop では受付を閉じたままにし、旧チェックポイントを残します。
旧ワーカーの自動復元や、ホスト資源・DB の移行を意味しません。

候補ロードと未 poll の factory は外部 I/O や共有資源への変更を始めない契約です。
OS の DLL 初期化も含めてこの契約を守る必要があり、メタデータだけでは検査できません。

## 論理的切り替えと物理回収

初期版の必須条件は受付先と管理対象の寿命を制御することです。
メッセージ API は KeepLoaded を使い、旧 DLL の自動回収はしません。
既定32枠の共有ロード予算は蓄積を区切るための累積試行数上限で、メモリ量の上限ではありません。
枯渇後は開発プロセスを再起動します。

物理回収には参照数に加え、DLL 呼び出しから戻ったこと、後で走る TLS・デストラクタ・コールバックがないことの確認が必要です。
この条件を確認できるホストには `unsafe reclaim_native_image` を提供します。
SDK は退役・所有参照・呼び出し帰還を再検査します。外部 Waker の帰還、TLS、依存先はホストの契約です。
手順と保持理由は [DLL の寿命](UNLOAD_SAFETY.md) を参照してください。

## 組み込み時の設計

ゲームへの適用ではフレーム境界、所有スレッド、旧非同期ジョブ結果を新しいワールドへ反映する条件を決めます。
[Bevy サンプル](BEVY_GAME.md) に、これらの境界を扱う最小構成を示しています。
世代 ID が違う結果を捨てても、既に発生した副作用は取り消せません。
子処理は明示登録の範囲で管理します。非同期ホストサービスと、複数所有スレッドからの
ホスト I/O キューを提供します。SDK ハンドルは所有スレッドで扱い、未登録処理の終了確認はアプリケーションが行います。
ホスト資源の移行はアプリケーションの確定フックで扱います。
具体的な受け入れ条件は [互換性と対象範囲](COMPATIBILITY.md)、実装契約は
[ホスト資源と受付](HOST_RESOURCES_AND_ROUTING.md) と [Restart](RESTART_AND_MIGRATION.md) にまとめています。
