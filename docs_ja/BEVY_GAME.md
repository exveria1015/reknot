# Bevy ゲームへの最小適用

[English](../docs/BEVY_GAME.md) | 日本語

Bevy **0.20.1** の `App` / `MinimalPlugins` / ECS を使い、1体の Actor の位置を
実 DLL の常駐ワーカーで進めるサンプルです。描画なしで実行し、更新時の規則を先に検証します。
ホストには Rust 1.97.1 以降が必要です。Bevy はホストだけに依存し、ロジック DLL は依存しません。

## 実行

リポジトリのルートで実行します。Cargo / rustc が PATH に必要です。

```powershell
cargo run -p bevy_game_host --locked -- --verify
```

速度1と速度3のロジックを別々にビルドし、有限フレームで検証して終了します。
ソースファイルは書き換えません。テストとして同じ検証を呼び出す場合は次を使います。
検証の期待値は配布時の `STEP`（通常1、`fast` 機能では3）に対応しています。
手動編集後にこの検証を行う場合は、その定数を元へ戻してください。

```powershell
cargo test -p bevy_game_host --test native_game --locked -- --ignored --test-threads=1 --nocapture
```

開発時の連続実行は次です。約60フレーム/秒で動き、60フレームごとに状態を出力します。
通常ジョブも60フレームごとに発行し、30フレーム後に返すようにしています。

```powershell
cargo run -p bevy_game_host --locked
```

`examples/bevy_game_logic/src/lib.rs` の `STEP` の値を変更して保存すると、Cargo を
別プロセスで起動します。ビルド中もフレームが進み、成功後に Restart します。
構文エラーなどのビルド失敗では現在のコードを使い続け、次の編集で再ビルドします。
監視対象はこの1ファイルだけです。プロトコルや依存関係を変更した場合はホストも再起動してください。
終了は Ctrl+C です。連続実行の終了操作は協調停止の検証ではなく、`--verify` が明示停止・完了を検査します。

ビルド出力とログは `target/bevy-game-build/<PID>/` に置きます。通常のホストビルドとは
別の target directory を使うため、テスト中の入れ子の Cargo がホストのロックを待ち続けません。
ロジックの初回ビルドはゲーム開始前に待機し、開始後は `Child::try_wait` で確認します。

## フレームと所有

| Bevy の段階 | 処理 |
| --- | --- |
| `PreUpdate` | フレーム番号更新、候補の受領、Drain の切り替え、Restart を1回 poll |
| `Update` | 新規ジョブの受付、常駐ワーカーと通常タスクを1回ずつ poll |
| `PostUpdate` | 返却メッセージを検査し、ホストが ECS に適用 |

切り替えは `PreUpdate` だけで行います。候補を prepare しただけでは世代は変わりません。
`Update` / `PostUpdate` では、フレーム開始時の世代が変わっていないことを assert します。
描画を追加する場合は、ゲーム状態の確定後にその状態を描画へ渡します。

`GameHost` は `Rc` と `RequestRouter` を持つ `!Send` / `!Sync` の型です。
Bevy の `NonSendMut` によって、DLL のロード・poll・サービス呼び出し・破棄を
所有スレッドに置きます。ホストとサービスでは所有スレッドの ID も検査します。
Bevy の `multi_threaded` 機能は有効ですが、DLL タスクをそのワーカープールへ移してはいません。

DLL へは JSON のバイト列、フレーム番号、版付きチェックポイントだけを渡します。
`World`、コンポーネントの参照、Bevy の内部レイアウトは共有しません。
ホストサービスは同期的に時計を読むか、長さを制限した返却キューに追加するだけです。
通常ジョブは最大8件、返却キューは最大64件、1メッセージは最大1024バイトです。
満杯なら明示的に拒否し、自動再実行はしません。

## 旧ジョブ結果の規則

このサンプルでは、状態を書き換える通常ジョブを次の順に検査します。

1. ジョブの世代が現在の有効世代と一致する。
2. 対象 Entity が存在する。`Entity::to_bits()` に再生成の世代も含め、同じスロットの別 Entity と区別する。
3. ジョブ発行時の `revision` が対象の現在の版と一致する。

すべて一致した結果だけ適用し、`revision` を進めます。この例のジョブは位置のスナップショットを
入力にしないため、毎フレームの移動では `revision` を進めません。経路探索などで位置も入力にする場合は、
位置の変更や許容する誤差に応じた失効規則も必要です。
これはアプリケーションの規則であり、リローダーがジョブ内容の有効性を自動判定するわけではありません。

Drain 後も旧ジョブは完了できますが、結果は旧世代として破棄します。
登録ワーカーも Drain だけでは再生成されないため、旧ワーカーの移動命令は適用されなくなります。
常駐ワーカーを新ロジックへ移す実用上の既定は **Restart** です。連続実行でも Restart を使います。

## 複数フレームの Restart

停止通知を受けた旧ワーカーは、意図的に2フレームの後処理を待ち、tick 数を保存して完了します。
ワーカーには `spawn_child` で登録した子もあり、停止通知後に次の poll まで後処理を待ちます。
登録枠が稼働中に1、停止完了時に0になることも実 DLL で検査します。
通常ジョブも停止通知を確認し、結果を発行せずに終了します。通常ジョブは再実行しません。

`Restart<'_>` を同じ構造体内の router へ自己参照させず、router を所有する
`async move` ブロック内で待機します。この future を次のフレームへ持ち越し、外側では
通常タスクも引き続き poll します。停止待ち中の新規要求は拒否します。
ホストの時計と ECS スケジュールは動作し続け、停止完了後の境界で新世代へ切り替えます。

チェックポイントのスキーマは同じ `TICKS` v1 のまま、tick 数をそのまま引き継ぎます。
型・形式変更の移行は既存の [Restart の説明](RESTART_AND_MIGRATION.md) と実 DLL テストが対象です。
後処理失敗などで Restart が失敗した場合、受付を停止したままにするコアの契約に従い、
この最小ホストではエラーを表示します。一般的な復旧 UI は実装していません。

## 検証範囲

`native_game` の統合テストは、描画なしで次を検査します。

- 別々に生成した速度1・速度3の実 DLL をロード。
- prepare では変化せず、3フレーム目の境界で Drain を適用。
- 遅れた旧世代結果の破棄、新世代の結果の適用、入力版不一致の破棄。
- Entity 削除後に同じスロットを再利用し、旧 Entity 宛て結果が新 Entity を変更しないこと。
- 旧 Drain 世代の常駐ワーカーと、長時間ジョブを含めた協調停止。
- 2フレーム以上 Pending のままフレームを進め、12フレーム目の境界で Restart を適用。
- 保存 tick 数と新ワーカーの開始値の一致、速度3での再開。
- 存在しない DLL の拒否後も世代と新規ジョブの受付を維持。
- 最後のワーカーの明示停止・完了、ホストとサービスの所有スレッド上での破棄。
- 通常の `App::run` でも120フレームまで実行し、常駐ワーカーと定期ジョブの結果が位置へ適用されること。

描画・入力・GPU 資源・物理エンジン、外部コールバックや管理外の子タスクの停止は、この検証に含めません。
性能測定や一般的なゲーム統合の完成を示すものでもありません。
生成した DLL は通常の KeepLoaded と累積ロード予算の契約に従います。
