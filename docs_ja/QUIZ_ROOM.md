# WebSocketクイズルーム：Axum + Reknot と Fastify + JS

[English](../docs/QUIZ_ROOM.md) | 日本語

問題・ブラウザー画面・メッセージ形式を共有する、実際に遊べるローカル比較です。
両方の部屋に参加し、問題ごとに一度回答できます。採点ルールを編集しながらプレイを続けられます。
アカウントやトークン、フロントエンドのビルドは不要です。

## 起動して遊ぶ

stable Rust/Cargo、ネイティブリンカー、Node.js 22以上とnpmを用意し、リポジトリのルートで実行します。

```sh
npm ci --prefix examples/quiz_room/js
node examples/quiz_room/start.mjs
```

ランチャーがAxumホストをビルドして両サーバーを起動し、準備ができるとURLを表示します。
Rustロジックの初回ビルドには時間がかかる場合があります。
`http://127.0.0.1:4101/` を開き、名前を入力して参加してください。
別タブを開くと対戦相手を追加できます。問題を開始し、それぞれのパネルで回答して得点を比較します。
全員が回答するか30秒の期限を過ぎると正解が表示され、次の問題に進めます。
5問を繰り返し、得点は累積します。終了した問題は参加者の誰でも次へ進められます。
ランチャーのターミナルでCtrl+Cを押すと両サーバーが終了します。

ポートを変更し、Drainで起動する場合：

```sh
node examples/quiz_room/start.mjs --mode=drain --rust-port=4201 --js-port=4202
```

表示されたURLを使ってください。クエリの `rust` と `js` が接続先のローカルポートを指定します。
ポート `0` ではOSが空きポートを選びます。npmがなくpnpmがある場合は、
`pnpm dlx npm@11 ci --prefix examples/quiz_room/js` で同じロックファイルから導入できます。

片方ずつ調べる場合は、個別に起動できます。

```sh
cargo run -p quiz_host --locked
node examples/quiz_room/js/server.mjs
```

各サーバーは `QUIZ_PORT` と `QUIZ_RELOAD_MODE`（`restart`／`drain`）を読みます。
既定値はポート4101／4102、Restartです。両方とも `127.0.0.1` のみにバインドし、同じ画面を配信します。
サーバーごとに独立したメモリー上の部屋が1つあります。得点はロジック更新を越えて残りますが、
切断したプレイヤーは削除され、サーバーを再起動すると部屋は初期化されます。
ローカル開発のサンプルであり、公開対戦サービスを構築するものではありません。

## 接続したまま編集する

| 編集 | Rustのソース | JavaScriptのソース | 確認すること |
| --- | --- | --- | --- |
| `POINTS`：100 → 150 | `examples/quiz_logic/src/lib.rs` | `examples/quiz_room/js/logic.cjs` | 次の正解が150点になり、既存の得点は変わらない |
| `LABEL`：rules-v1 → rules-v2 | 同上 | 同上 | ルール名と回答を受け付けた世代 |
| `TICK_MS`：200 → 100 | 同上 | 同上 | Restartでは時計を再生成し、Drainでは旧周期が続く |
| 構文エラーを入れる | 同上 | 同上 | 候補が失敗し、旧世代で処理を継続する |
| `CONTRACT_VERSION`：1 → 2 | 同上 | 同上 | 旧処理を止める前に候補を拒否する。1に戻すと復旧する |

「次の回答を10秒待たせる」を選んで回答し、待機中にロジックを保存してください。
更新方式によって結果が変わります。

| 挙動 | Restart（サンプルの既定値） | Drain |
| --- | --- | --- |
| 切り替え中の新規受付 | 切り替え完了まで待つ | 受付時点の世代を使う |
| 受付済みの遅延回答 | キャンセルと終了を待つ。加点・自動再送なし | 問題が受付中なら旧ルールで完了する |
| 登録した時計 | 停止・終了後にカウントのチェックポイントから再生成 | 元のワーカーが動き続ける |
| 接続・部屋・得点・期限 | ホストが所有し、保持する | ホストが所有し、保持する |
| ビルド・契約の不一致 | 現在の世代を継続する | 現在の世代を継続する |

キャンセル後、問題が受付中なら自分で回答し直せます。採点の計算が成功していても、
完了時にその問題の受付が終わっていれば加点しません。画面には採点世代・時計世代・
チェックポイントのカウント・イベントログを表示します。Drainで採点と時計の世代が異なるのは想定した挙動です。

## フレームワークとの接続

AxumホストはマルチスレッドのTokioランタイムを使います。`LocalSet` により、
`DevModule`・ネイティブタスク・終了処理を1つの所有スレッドに置きます。
Axumの `Send` なWebSocketタスクは `DevModule::bridge` の `HandlerClient` を使い、
10msごとの `update()` が通常の通信中も処理を進めます。ロジックをawaitする間、部屋のMutexは保持しません。
登録した時計は上限付きのホストsleepサービスを待ち、カウントを保存してコピーした通知を送ります。
ソケット・プレイヤー・問題・期限検査・回答予約・得点の確定はホストが担当します。

Fastifyホストは公式WebSocketプラグインをルートより前に登録し、ソケットのリスナーを同期的に取り付けます。
サンプルの更新処理はCommonJSモジュールを読み直して明示した契約を検査し、受付時の実装を捕捉します。
Restartでは `AbortController` で中止を要求し、Promiseの終了を待ちます。
部屋と時計のチェックポイントはこちらもホストが持ちます。この更新処理はアプリ側の実装であり、
Fastify自体のホットリロード機能や汎用JavaScript更新ライブラリではありません。

| 比較対象 | Axum + Reknot | Fastify + JavaScript |
| --- | --- | --- |
| 更新単位 | ロジックcrateと監視対象のローカル依存 | `logic.cjs` のみ。補助依存は読み直さない |
| 反映方法 | Cargoのdebugビルド、ネイティブロード、型付き契約検査 | モジュール再読み込みと明示した実行時契約の検査 |
| 構造の契約 | Rust／Serdeの型から両方向を生成 | 手書きの宣言。JSの型構造は自動推定しない |
| ライフサイクルの実装 | Reknotの型付きブリッジ・登録ワーカー・ホストサービス | サンプルの更新処理と中止可能なPromise |
| 保存のデバウンス | 200ms | 200ms |
| 維持するフレームワーク部分 | AxumのリスナーとWebSocketセッション | FastifyのリスナーとWebSocketセッション |

スキーマ照合は保守的な構造検査で、意味の互換性は証明しません。プロトコルの変更では
ホストも再ビルド・再起動する必要があります。このサンプルの保存時Restartはワーカー状態の契約が
同じ場合に対応し、任意の変更を自動移行しません。明示的な移行は [型付きRestart](TYPED_RESTART.md)、
診断とスキーマ出力は [契約エラーとスキーマ](CONTRACTS_AND_SCHEMAS.md) を参照してください。

## 検証と計測

```sh
npm ci --prefix examples/quiz_room/js
cargo clippy -p quiz_host -p quiz_logic -p quiz_protocol --all-targets --locked -- -D warnings
node examples/quiz_room/check.mjs
```

`--js-only`／`--rust-only` で対象を絞れます。検証スクリプトはOSの短い一時ディレクトリ内の
分離コピーだけを編集し、空きポートで実サーバーを起動して、2つの実WebSocketクライアントを接続します。
正解・不正解、二重回答・古い問題への回答・不正選択肢・期限切れの拒否、得点と接続の維持、
Drain／Restart中の回答、時計の連続性と周期、構文・契約の拒否、状態スキーマの構造不一致、復旧を検査します。
ビルド時間を確保するため検証用の問題は長い期限にし、別の短い問題で期限切れを確認します。
CIのcoreジョブでもWindowsとLinuxで実行します。

`target/quiz-check/results.json` に、各バックエンド・方式のウォーム状態での編集1回について、
ファイル書き込みからクライアントが新世代を観測するまでの時間と実行環境を記録します。
デバウンスとRustのコンパイルを含みます。ログと一時コピーは失敗調査のため保持します。
この計測だけではスループット、本番のレイテンシー、メモリー使用量、一般的な性能順位は判断できません。
速度を主張するなら同じ環境で反復して比較してください。導入コードの量、診断の分かりやすさ、
ライフサイクルの理解しやすさも評価対象です。

## 制限と参考資料

接続は32、ソケットごとの処理中コマンドは4、受信メッセージは4KiBまでです。
Rustのブリッジは128スロット・同時実行32要求に制限します。送信を受け取れないクライアントは切断します。
部屋は一時的な状態で、認証・再接続時の本人識別・永続化・外部公開は対象外です。
編集するネイティブ／JSコードは信頼できるものを前提にします。JS候補の読み込みではトップレベルの
コードも実行されるので、モジュール初期化に外部への副作用を持たせないでください。
この更新処理は任意のユーザーコードの副作用を取り消せず、停止に協力しない処理や無限ループを強制終了できません。

RustのDLLはSDK既定の累積32回の試行予算内で保持します。上限に達したらホストを再起動してください。
自動アンロードは行いません。ホストコード・問題・画面は起動時に読み込むため、編集後はサーバーの再起動が必要です。
`QUIZ_LOGIC_MANIFEST`（Rust）と `QUIZ_LOGIC_PATH`（JS）は、検証用の信頼できるローカルソースを選ぶための設定です。
ソケットメッセージからは変更できません。
