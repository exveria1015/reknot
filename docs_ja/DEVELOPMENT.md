# 開発時の運用

[English](../docs/DEVELOPMENT.md) | 日本語

型付き API の `DevModule` は、編集の検出からビルド、更新候補の適用までを扱います。
このページでは、普段の開発での動きと、ホストを独自に組む場合の条件を説明します。

## ビルドと切り替え

初回起動では、ビルドとロードが終わってから要求の受付を始めます。
起動後は、ホストが `DevModule::update()` を定期的に呼び、次の流れを進めます。

1. ソースの変更通知を受け取る。通知は既定で200msまとめます。
2. バックグラウンドでビルドする。ビルドは1本ずつ実行します。
3. 完成した候補の契約を検査し、成功すれば新しい要求の受付先を切り替える。

ビルド中も、現在の世代へ要求を渡せます。すでに受け付けた処理は、その世代で完了まで続きます。
追加の編集通知を受け取った場合は、古くなったビルド結果を破棄して再ビルドします。

`update()`は`DevModule::bridge`で作成したブリッジ・登録ワーカーの実行とキャンセル後の終了処理も進めます。
要求をその周期から独立させる場合は`development.host().bridge(...)`を使い、返された`BridgeDriver`を
executorで直接駆動します。終了待ちの間もdriverを駆動してください。
既定は Drain です。`DevOptions::with_reload_mode(ReloadMode::Restart)` で [型付き Restart](TYPED_RESTART.md) を選べます。
事前検査後に受付を止め、ルートと子処理の終了を待って切り替えます。停止開始後の失敗では受付停止を維持します。
Restart 待機中の編集はその完了後に処理します。開始済みの停止を巻き戻すことはありません。
入力待ち、要求の実行中、終了待ちの間も呼び続けてください。
`DevModule` の破棄で監視と適用は終わりますが、開始済みの Cargo プロセスは完了まで続きます。

## ソース監視の範囲

Cargo の依存関係から、ロジックとローカル依存先の入力を調べます。

| 監視するもの | 範囲 |
| --- | --- |
| Rust ソース | ロジックとローカル依存先の`src/`、Cargoターゲットの入口と、そのディレクトリ配下の隣接・入れ子の`.rs`モジュール |
| crate の設定 | 各 `Cargo.toml` と `build.rs` |
| Cargo の設定 | workspaceの`Cargo.toml`・`Cargo.lock`、指定manifestのディレクトリから祖先までにある`.cargo`内の`config` / `config.toml`。起動後に作ったディレクトリも対象 |

Cargoのmetadataとbuildは指定manifestのディレクトリから起動し、ホストの起動場所によらず対象の設定を読みます。
`implementation/lib.rs`やcrateルートの`lib.rs`など、標準の`src/`以外の配置にも対応します。
各crateの`target/`、設定されたCargo出力先、`.git`は入力から除外し、その出力先内にソースを置く構成は拒否します。
独自のbuild scriptでも、監視するソース配下への生成は避けてください。

監視範囲外の include ファイルや独自生成入力を変更したら、監視対象のソースも保存するか、ホストを再起動します。
監視対象のディレクトリを作成・削除・置換すると、OSへの監視登録を更新します。
同じパスへの作り直しや、ディレクトリの欠落・設定の誤りによるビルド失敗の後も、修正して保存すれば更新を検出します。

依存宣言が変わると監視範囲を更新し、新しい監視の下で再ビルドしてから適用します。
ビルドは `--locked` で行うため、依存の追加で `Cargo.lock` の更新が必要になったら、通常の Cargo 操作で先に更新してください。
SDK や ABI 自体の変更では、ホストとロジックを再ビルドし、ホストも再起動します。

監視は、OS から届いた通知を基準にしています。
通知の欠落や遅延をなくす保証や、ファイルシステム全体を同時点の状態で読み取る保証はありません。

## 失敗からの復旧

起動後の更新に失敗した場合は、次のように扱います。

| 状況 | 挙動と対処 |
| --- | --- |
| コンパイルエラー | 動作中の世代を維持する。ログを確認し、修正して保存する |
| 更新候補の契約不一致 | 受付先を切り替えない。共有プロトコルを確認し、意図した契約変更なら版を上げてホストも再起動する |
| 監視のエラー | 表示されたパスを確認する。保存に反応しなくなった場合はホストを再起動する |
| ロード予算の枯渇 | ロードを止め、開発ホストを再起動する |

失敗した要求や完了したイベントの自動再実行はありません。
実行時の panic や業務上のエラーは、ビルド失敗による旧世代の維持とは別に扱います。
症状から調べる場合は [トラブルシューティング](TROUBLESHOOTING.md) を参照してください。

## 上限と観測

受付先の世代、実行中の要求数、ビルド・ロードエラー、停止待ち、ロード予算、DLL のコピー先を記録すると、
切り替えの状態を追えます。Restart を使う場合は、ワーカーの状態とチェックポイントのサイズも記録します。

`in_flight()` は、登録した子処理の終了待ちを含むルート要求の数です。
要求を Drop しても、登録処理が残れば減りません。管理外タスクや未登録コールバック、DLL の数は表しません。

ロード予算は既定32枠です。失敗・破棄候補も含む累積ロード試行数を数え、メモリ使用量は制限しません。
Router を作り直す場合も同じ `GenerationBudget` を共有すると、セッション全体で同じ枠を使えます。
DLL を明示回収しても、消費した枠は戻りません。

型付きの入出力とキューの上限は [API リファレンス](API_REFERENCE.md#容量と受付の上限) にまとめています。
低レイヤーでは入力・送信キュー・I/O の上限をホストで別に設けます。
Restart のチェックポイントは、既定で1ワーカーあたり1 MiBです。

### DLL とコピーの扱い

既定の `KeepLoaded` では DLL とコピーが蓄積します。
型付きホストは、完了済み旧世代の Router 参照を解放しますが、DLL を自動では回収しません。
明示回収を実装する場合は、切り替え前に `host.artifact_id()` を記録し、[回収の契約](UNLOAD_SAFETY.md) を確認してください。
回収が保留されても、新しい世代への受付切り替えとは別に扱います。

コピー先はユーザー一時領域の `reknot/managed-v1/sessions/<SessionId>/copies/` です。
`retention_snapshot()` で SDK の保持状況、`reknot-cache inspect` でファイルを観測します。
終了済みの適格なセッションは `reknot-cache clean --apply` で掃除できます。
旧 `<PID>/` 形式や不明な対象は、apply を指定しても削除しません。
手順は [保持量の観測とコピーの掃除](RETENTION_AND_CLEANUP.md) を参照してください。

## 低レイヤーで更新を制御する

`RequestRouter` 自体は Cargo やソース監視を起動しません。
`service_host` は同期ビルド、Tauri サンプルは子プロセスでの背景ビルドを使います。
`dev-tools` feature の `reknot::development` には、ビルド・パス・監視の補助があります。
独自のビルド手順で作った成果物を渡すこともできます。

低レイヤーの`SourceWatcher`の監視範囲は、そのcrateの`src/`・`Cargo.toml`・`build.rs`です。
`source_changed`を呼び続けると、ディレクトリの削除・再作成後に監視を登録し直します。
起動時に`src/`がない場合、manifest・build scriptの置換、新しいbuild scriptの作成にも対応します。
`src/`外の無関係なファイルや`.git`内の変更ではビルドを起こしません。ビルド出力は`src/`外に置いてください。
独自のCargoターゲット・ローカル依存先・Cargo設定の探索には、`DevModule`または独自の監視設定を使います。

ビルド後に `unsafe prepare(path)` で候補をロード・検査し、`activate` で Drain、
または `restart` で登録ワーカーの停止・移行・再生成を行います。
古い候補や別 Router の候補は、対象 Router の現在世代から準備し直してください。

候補の準備では、共有資源の変更や外部送信を始めない契約です。DLL の初期化コードにも適用されます。
旧新世代が共存できるサービス契約を維持してください。
ABI・サービス・状態スキーマの照合は、データの意味やネイティブコードの安全性の証明にはなりません。

### Restart の失敗と中断

Restart の停止待ち中は、外部で所有している通常タスクの poll も進めます。
必要ならホスト側で待機期限を設けますが、poll から戻らない処理を同じスレッドの timeout で安全に強制停止することはできません。

受付停止後に移行が失敗した場合や、Restart の Future を Drop した場合は、受付停止と旧チェックポイントを維持します。
再試行するか、復旧方針を決めて `resume()?` を呼びます。`resume` は旧ワーカーを再生成せず、I/O も取り消しません。
詳しくは [Restart と状態移行](RESTART_AND_MIGRATION.md) を参照してください。

本番配信、クラッシュ隔離、外部副作用の自動巻き戻しは対象外です。
利用条件は [互換性と対象範囲](COMPATIBILITY.md) を参照してください。
